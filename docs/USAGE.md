# Работа со станцией КНС-1: имитация, испытания, перенос на объект

Как запустить станцию в имитации без железа, менять приток, вводить отказы, смотреть тревоги и журнал,
прогнать сценарии ПМИ и прочитать отчёт — и как перенести проект на реальный объект. Короткая версия —
[README](../README.md#быстрый-старт). Установка CODESYS, coUnit и рантайма — [MANUAL_STEPS.md](MANUAL_STEPS.md);
алгоритмы — [04_algorithms.md](04_algorithms.md); программа испытаний — [06_PMI.md](06_PMI.md); устройство
модели и сценариев — [DESIGN.md](DESIGN.md), разделы 3.3, 11, 14.3.

Команды — из корня репозитория. Команды CODESYS и рантайма — только Windows; в примерах cmd, в
PowerShell переменная задаётся как `$env:PMI_LIVE = "1"`.

меньше заданного запаса.

## 2. Запуск имитации

Один раз — подготовить рантайм и проверить библиотеки (plc-process-lib 1.0.0.0, CAA File, SysTimeRtc,
coUnit):

```bat
python tools\codesys\cds.py runtime init
python tools\codesys\cds.py deps --check
```

Если библиотеки plc-process-lib нет в репозитории библиотек CODESYS, `cds.py deps` соберёт и установит её
из соседнего клона `../plc-process-lib` (в рабочей копии `git worktree` путь задаёт `PL_REPO`).

Запуск приложения имитации:

```bat
python tools_project\codesys\sim.py start --need-min 60
```

Скрипт выполняет по порядку:

1. `cds.py import` — проект `build\<имя каталога>.project` из `src/` с объектом Persistent Variables;
2. `symbol_config.py --build sim` — символьная конфигурация OPC UA сборки имитации: `GVL_Sim.stSimCmd`,
   `stSimCfg`, `stFaultInj` и команды станции доступны на запись, состояние — на чтение;
3. запуск рантайма или перезапуск, если до конца двухчасового демо-режима меньше `--need-min` минут;
4. сертификат OPC UA-сервера и доверие клиенту сценариев (`sim.py pki`);
5. загрузка приложения и «Старт» (скрипт CODESYS `sim_cds.py`), проверка входа по OPC UA.

`--no-import` пропускает шаги 1–2, если проект уже собран. Журнал шагов CODESYS — `build\sim-start.log`.
Коды выхода: 0 — успех, 1 — шаг не выполнен, 2 — неверные аргументы.

После старта (ожидаемое по PMI-01): `GVL_Sim.xSimulation = TRUE`, тревога `KNS1.SIM` (100013, Low) — норма
стенда; после первой загрузки станция в «Ручном» и через 600 с выдаёт `KNS1.NOAUTO`. Исходное
состояние испытаний И0 (уровень 1,20 м, приток 100 м³/ч, «Автомат», насосы, LIC101 и вентилятор в `Auto`) —
[06_PMI.md](06_PMI.md), раздел 5.2; его одной командой ставит исполнитель сценариев (пример в разделе 3.4).

| Команда | Что делает |
|---|---|
| `python tools_project\codesys\sim.py reset warm` (`cold`) | тёплый (холодный) сброс приложения и «Старт» без загрузки |
| `python tools_project\codesys\sim.py pki` | сертификаты OPC UA заново; при изменениях — перезапуск рантайма |
| `python tools_project\codesys\sim.py stop` | остановить процесс рантайма (приложение и OPC UA-сервер — вместе с ним) |

## 3. Приток, ливни и отказы по OPC UA

Модель и инъекции отказов управляются переменными `GVL_Sim` — теми же, что кнопки экрана «Имитация»
([08_hmi_spec.md](08_hmi_spec.md), раздел 10). Пока графики WebVisu нет, их пишут по OPC UA (сценарии,
свой скрипт, клиент OPC UA) или в окне наблюдения CODESYS после входа в приложение. Инъекции действуют
только при `GVL_Sim.xSimulation = TRUE`.

### 3.1 Подключение

| Параметр | Значение |
|---|---|
| Адрес | `opc.tcp://localhost:4840` |
| Безопасность | Basic256Sha256, Sign & Encrypt; вход по имени и паролю |
| Учётные данные | `%USERPROFILE%\.local\plc-tools\cds-runtime\credentials.json` (или путь в `CODESYS_RUNTIME_CREDENTIALS`) — тот же файл, что у `cds.py` |
| Сертификат клиента | `%USERPROFILE%\.local\plc-tools\opcua-client\` — создаётся при первом запуске; `sim.py pki` кладёт его в доверенные рантайма |
| Узел переменной | `ns=<индекс>;s=\|var\|CODESYS Control Win V3.Application.<путь>`, индекс — пространство имён, оканчивающееся на `IecVarAccess` |
| Предел запроса | не больше 100 узлов в одном чтении или записи |

Клиент сценариев `kns_scenarios.backend_opcua.OpcUaClient` делает всё это сам: находит пространство имён
и устройство, делит пакеты по 100 узлов, пишет значения в типе узла. Другой клиент OPC UA (например,
UaExpert) попадёт в отклонённые сертификаты: перенести его в доверенные — запасной путь
[MANUAL_STEPS.md, раздел 9.5](MANUAL_STEPS.md#95-сценарии-пми-scenarios).

### 3.2 Команды модели

Сокращения: `SimCmd` = `GVL_Sim.stSimCmd`, `SimCfg` = `GVL_Sim.stSimCfg`. Импульсы модель сбрасывает сама.
Полная таблица — [06_PMI.md](06_PMI.md), раздел 5.4.

| Что сделать | Запись |
|---|---|
| ускорить весь контур (1…50) | `SimCfg.rTimeScale := 20.0` |
| постоянный приток вместо суточного профиля | `SimCmd.xInflowOverride := TRUE`, `SimCmd.rInflowOverride_m3h := 180.0` |
| вернуть суточный профиль и ливни по seed | `SimCmd.xInflowOverride := FALSE` |
| время суток модели (профиль 27…112 м³/ч, среднее 70) | `SimCmd.rTimeOfDay_h := 7.0`, импульс `SimCmd.xSetTimeOfDay` |
| ливень сейчас (при `xInflowOverride = FALSE`) | `SimCmd.rStormPeak_m3h := 200.0`, `SimCmd.tStormDuration := T#30M`, импульс `SimCmd.xStormNow` |
| уровень в резервуаре | `SimCmd.rSetLevel_m := 2.0`, импульс `SimCmd.xSetLevel` |
| начальное состояние модели (уровень 1,20 м, ливни сняты, ПЧ готовы) | импульс `SimCmd.xResetPlant` |
| снять все инъекции | импульс `SimCmd.xClearFaults` |
| что считает модель: истинный уровень, приток, подачи, частоты, токи, время суток, перелив | чтение `GVL_Sim.stSimSts` |

Насосу на 100 % при уровне 1,4 м модель даёт ≈ 150 м³/ч, двум — ≈ 198 м³/ч: приток 180 м³/ч требует
подпорного насоса, а 250 м³/ч больше подачи всей станции (PMI-20).

### 3.3 Инъекции отказов

`Inj` = `GVL_Sim.stFaultInj`, индекс насоса 1…3 = Н1…Н3. Что видит ПЛК и какая проверка ПМИ этим
пользуется (полный список — [06_PMI.md](06_PMI.md), раздел 5.4):

| Отказ | Запись | Ожидаемая реакция | ПМИ |
|---|---|---|---|
| авария ПЧ | `Inj.axVfdFault[2] := TRUE` | `P102.EXT` (124, Medium), Н2 в отказе, пуск резервного, `KNS1.ATS` | PMI-13 |
| нет подтверждения пуска | `Inj.axNoFeedback[i] := TRUE` | отказ насоса, АВР | PMI-12 |
| потеря связи с ПЧ | `Inj.axVfdCommLoss[1] := TRUE` | `P101.COM` (116, Medium) через 3 с, насос работает, ПЧ через 5 с на 50 Гц | PMI-28 |
| обрыв уровнемера LT101 | `Inj.aeAiFault[1] := E_SimAiFault.WireBreak` (число 1) | через 2 с `LT101.FAIL` (1014), `KNS1.FLOAT`, управление по поплавкам | PMI-25 |
| поплавок LS102 не срабатывает | `Inj.eLs102Stuck := E_SimFloatStuck.StuckNormal` | аварийный режим по `LT101.HH` без поплавка; уровень выше 4,40 м дольше 30 с — `KNS1.LDEV` | PMI-24 |
| пропадание напряжения | `Inj.xPowerLoss := TRUE`, затем `FALSE` | `ES301.ALM` (3010, High), насосы стоят без отказов; после восстановления — последовательный пуск | PMI-33, PMI-34 |
| сухой ход насоса, засор, перегрев | `Inj.axAirLock[i]`, `axClog[i]`, `axOverheat[i]` | недогрузка или перегрузка по току, перегрев — авария ПЧ и АВР | PMI-15, PMI-16 |
| «Местное» на насосе | `Inj.axLocal[i] := TRUE` | насос выведен из автоматики станции | PMI-31 |

Перечисления по OPC UA пишутся числом базового типа; исполнитель сценариев переводит литералы
`E_SimAiFault.WireBreak` в числа по таблице `scenarios/kns_scenarios/enums.py`.

### 3.4 Пример: демонстрация на Python

Фрагмент для интерактивного Python (`python -i` из корня репозитория) на работающем приложении имитации:
исходное состояние, приток больше подачи одного насоса, авария ПЧ, чтение тревог и журнала. Он
пользуется тем же исполнителем, что сценарии ПМИ.

```python
import sys

sys.path.insert(0, "scenarios")
from kns_scenarios.alarms import AlarmView, load_alarm_list
from kns_scenarios.backend_opcua import OpcUaClient
from kns_scenarios.context import ScenarioContext
from kns_scenarios.credentials import load_credentials
from kns_scenarios.enums import ENUMS
from kns_scenarios.journal import EventFeed
from kns_scenarios.scenario import Runner

plc = OpcUaClient(credentials=load_credentials()).connect()
ctx = ScenarioContext(plc, enums=ENUMS)
alarms = AlarmView(plc, load_alarm_list(), ENUMS)
feed = EventFeed(plc)

ctx.set_time_scale(20)  # весь контур ×20
Runner(ctx, "opcua").initial_state({"method": "Stepped"})  # И0: «Автомат», ступенчатое, 100 м³/ч
feed.start_at_end()  # журнал — с этого момента

ctx.write({"GVL_Sim.stSimCmd.rInflowOverride_m3h": 180.0})  # больше подачи одного насоса
ctx.wait("GVL_Station.stStationSts.uiPumpsRunning = 2", timeout_s=900)  # подпорный с 2,40 м (PMI-03)
ctx.write({"GVL_Sim.stFaultInj.axVfdFault[1]": True})  # авария ПЧ Н1
ctx.hold(30)  # 30 с контура = 1,5 с при ×20
print({alarms.code_of(i): s for i, s in alarms.states().items()})
for r in feed.poll():
    print(r.seq, alarms.code_of(r.id), r.new_state, r.value, round(r.mono_s, 1))
ctx.clear_faults()
plc.close()
```

Таймауты `wait` и `hold` — во времени контура: исполнитель делит их на ускорение. По ПМИ ожидается:
Н1 — ведущий с 1,60 м, на 2,40 м через 5 с пускается Н2 (PMI-03); после аварии ПЧ Н1 — `P101.EXT`
ActiveUnack, пуск резервного Н3 и `KNS1.ATS` (как PMI-13 для Н2). Числа состояний — `E_AlarmState`: 1 —
ActiveUnack, 3 — RtnUnack. Вызовы фрагмента проверены на имитаторе OPC UA-сервера из тестов
(`scenarios/mock_plc.py`); реакцию станции на рантайме проверяют сценарии ПМИ.

## 4. Тревоги и журнал

**Тревоги.** `GVL_Log.stAlarmView` — все тревоги не в `Normal` (в том числе отложенные и подавленные):
строки `astRow[n].udiId` (номер) и `eState` (состояние ISA-18.2), число строк — `uiCount`, всего не в
норме — `uiActiveTotal`. Номера: устройства — `dev_no · 10 + слот` (например, `P101.EXT` = 114), станция —
от 100 000 (`KNS1.*`), регулятор — 100 100; коды, тексты, приоритеты и действия оператора —
[05_alarm_list.csv](05_alarm_list.csv). Квитировать все — импульс `GVL_Station.stStationCmd.xAckAll`, одну
по номеру — `stStationCmd.udiAckId`.

**Журнал.** Кольцо на 200 записей в памяти ПЛК: тревоги устройств и станции, события станции
(номер 101000 + код, таблица — [04_algorithms.md](04_algorithms.md), раздел 16), смена режимов
устройств. Два способа читать:

- курсор внешнего клиента `GVL_Log.stEventFeed`: клиент пишет `udiFromSeq` — первый нужный номер, ПЛК
  отдаёт до 32 записей от старой к новой (`astRow`, поля `udiSeq`, `udiId`, `eOldState`, `eNewState`,
  `rValue`, `uliUtc_ms`, `lrMono_s`); так читает журнал `EventFeed` (раздел 3.4);
- страница HMI `GVL_Log.stEventView`: номер страницы — `uiPage`, по 20 строк, новые сверху.

`lrMono_s` — время процесса с ускорением: интервалы между событиями по нему точны до цикла задачи при
любом ускорении. После сброса или перезапуска ПЛК номера журнала начинаются с 1.

**Выгрузка в CSV.** Импульс `GVL_Station.stStationCmd.xExportLog`: снимок журнала пишет `PRG_Slow` в
`SlowTask` через CAA File, состояние — `GVL_Station.stStationSts.eLogExport`, итог — событие 101019 с числом
строк. Файл `kns_events.csv` — в рабочем каталоге рантайма; у пользовательского процесса это
`%LOCALAPPDATA%\VirtualStore\Program Files (x86)\CODESYS 3.5.17.30\GatewayPLC\`. Формат — ASCII, `;`, CRLF:

```text
seq;time_utc;kind;id;code;priority;old_state;new_state;reason;value
1532;2026-10-16T07:41:05.120Z;alarm;110;P101.FTS;2;0;1;1;0.0
1533;2026-10-16T07:41:05.140Z;station;101006;KNS1.E6;0;0;0;0;3.0
```

Русских текстов в файле нет: их подставляют по коду из 05 и таблицы событий 04, раздел 16.

## 5. Сценарии ПМИ и протокол

**Без ПЛК** — офлайн-проверка 39 файлов сценариев (пути переменных — по объявлениям `src/`, права записи —
по символьной конфигурации, номера и названия — по 06) и тесты исполнителя на имитаторе OPC UA-сервера:

```bash
python -m pytest scenarios
```

**На рантайме** — после `sim.py start` (раздел 2):

```bat
set PMI_LIVE=1
python -m pytest scenarios\test_pmi.py -m plc -k "PMI-13"
python -m pytest scenarios\test_pmi.py -m plc
```

Первая команда pytest — одна проверка, вторая — все 39. Каждый сценарий сам приводит станцию в И0,
задаёт ускорение (по приложению А программы: обычно ×20, PMI-39 — ×50), вводит воздействие, ждёт реакцию
и сверяет состояния, тревоги и записи журнала. Серия — около 1,7 ч реального времени: её делят на части
с перезапуском рантайма между ними, `sim.py start --no-import --need-min <минут части>`.

| Переменная | Что задаёт |
|---|---|
| `PMI_LIVE=1` | включить сценарии на рантайме (без неё они пропускаются) |
| `PMI_OPCUA_URL` | адрес сервера, по умолчанию `opc.tcp://localhost:4840` |
| `PMI_RESET` | шаги сброса приложения (PMI-10, PMI-35): `sim` — через `sim.py reset` (по умолчанию, если задан `CODESYS_EXE`), `none` — такие шаги «не проверялось» |

**Отчёт исполнителя** — `build\pmi-results.md` и `build\pmi-results.json` (не в git). В `.md` — строка на
проверку: итог («соответствует», «не соответствует», «не проверялось»), вид (авто или авто с ручной
частью), исполнитель, ускорение k, измеренные задержки, что отмечается вручную, замечания — несработавшие
сверки с фактическим значением. В `.json` — все сверки каждого шага.

**Протокол** — [07_test_protocol.md](07_test_protocol.md): его заполняет инженер по отчёту исполнителя.
Вручную в нём отмечают то, что сценарий не видит: вид экранов, права ролей, содержимое файла CSV. В
репозитории — заполненный протокол № 1 от 19.10.2026 (39 из 39 соответствуют, у пяти проверок — по
автоматической части) и отчёт исполнителя по частям серии — [07_pmi_report.md](07_pmi_report.md); для
своего прогона документ служит бланком.

**Файл сценария** — `scenarios/pmi/PMI-NN.toml`, номер совпадает с проверкой 06. Ключи: `[setup]` (способ,
уровень, приток, наработка), шаги `[[step]]` — `write`, `pulse`, `mark`, `wait`, `wait_alarm`, `expect`,
`expect_event`, `expect_delay`, `hold_s`, `time_scale`; `[teardown]`. Пример — PMI-13 в
[README](../README.md#как-это-выглядит), схема — [DESIGN.md](DESIGN.md), раздел 14.3. После правки
перечислений в `src/DUTs` — `python tools_project/gen_enums.py`.

## 6. Перенос на реальный объект

Что остаётся как есть: логика станции (`src/POUs/Station`), журнал и сводка тревог (`src/POUs/Log`),
модель и часы, обвязка сценариев. Что меняется: перечень сигналов, адаптер ПЧ, уставки, параметры модели
и сборка для своего ПЛК.

### 6.1 Перечень сигналов и iolistgen

`docs/03_io_list.csv` — UTF-8, разделитель `;`, строка на сигнал. Главные колонки: `tag`, `signal_type`
(AI, DI, DO, MB), `device`, `device_type` (`AnalogInput`, `DigitalInput`, `MotorVfd`…), `dev_no` (из него —
номера тревог), `range_min`/`range_max`, уставки `sp_hh`…`sp_ll`, задержки, `alarm_priority`,
канал модуля `io_module`/`io_channel`, регистр Modbus `mb_link`, `mb_slave`, `mb_func`, `mb_reg`, `mb_type`,
параметры ФБ в `params`. Описание формата — документация iolistgen; итоговая таблица проекта —
[03_io_list.md](03_io_list.md).

После правки перечня:

```bash
python tools_project/generate.py
python tools_project/check_docs_consistency.py
```

`generate.py` запускает iolistgen с настройками `iolistgen.toml` (часы контура, приёмник тревог, блок
станции в `GVL_Persist`) и перестраивает `src/*/Generated`, карты Modbus `docs/modbus_*.csv`, импорт SCADA
`scada/`, `docs/alarms.csv` и `docs/03_io_list.md`. Сгенерированные файлы руками не правят и коммитят вместе
с перечнем; `generate.py --check` (CI) ловит забытую генерацию. Блок станции `GVL_Persist` —
`tools_project/persist_station.txt`: новые объявления только в конец, иначе сдвинутся сохранённые
значения.

**Пример: уставка HH уровнемера 4,0 → 3,9 м.** В строке `LT101` колонка `sp_hh`: `4` → `3,9`.

```text
LT101;Уровень в приёмном резервуаре;AI;;AnalogInput;101;PV;;0;5;м;3,9;3,5;0,8;0,5;3;;High;Резервуар;A1;1;…
```

`generate.py` печатает `файлов: 17, изменено: 17`: SHA-256 перечня есть в заголовке каждого
сгенерированного файла. Без строк заголовка (`git diff --stat -I "SHA-256"`) меняются 7 файлов: сам перечень, `GVL_CfgProject.gvl.st` и `GVL_Persist.pvl.st`
(`rSetpoint_eu := 4.0` → `3.9` у предела HH), `docs/alarms.csv`, `scada/scada_alarms.csv`,
`scada/scada_tags.csv`, `docs/03_io_list.md`. Сверка документов выдаёт 8 расхождений — что править руками:

```text

ARCHITECTURE.md:296: [C03] SHA-256 перечня 06336d13c4b2, в docs/alarms.csv — 07afb9af7961
```

значения остаются прежними, к уставкам проекта их возвращает команда `GVL_Hmi.xApplyProjectCfg` («Применить уставки

### 6.2 Адаптер ПЧ под реальную модель

Устройство «насос с ПЧ» — `PL.FB_MotorVfd` библиотеки; регистры ПЧ оно не знает. Между `GVL_IO` и
устройством стоит адаптер: `FB_VfdAdapter_Cond` для условной карты ([ARCHITECTURE.md](ARCHITECTURE.md),
раздел 12):

| Регистр (слейв 1–3, RS485-1) | Функция | Переменная `GVL_IO` | Что |
|---:|---|---|---|
| 0 | FC16 | `wP101_CTW` | слово управления: бит 2 — сброс аварии; пуск — проводом |
| 1 | FC16 | `uiP101_FREF` | задание частоты, 0,01 Гц (5000 = 100 %) |
| 100 | FC3 | `wP101_STW` | слово состояния: готов, в работе, авария, предупреждение, от клемм |
| 101 | FC3 | `uiP101_FACT` | фактическая частота, 0,01 Гц |
| 102 | FC3 | `uiIT111` | ток двигателя, 0,1 А (устройство `IT111`) |
| 103 | FC3 | `uiP101_FCODE` | код последней аварии (на фейсплейте) |

Для своего ПЧ:

1. В перечне поменять регистры, функции и типы в колонках `mb_*` строк `P10n_CTW`, `P10n_FREF`, `P10n_STW`,
   `P10n_FACT`, `IT1n1`, `P10n_FCODE` (у реального ПЧ слово может быть другим, а частота — в другом
   масштабе) и перегенерировать слой (раздел 6.1).
2. Написать `FB_VfdAdapter_<Модель>` с теми же выходами, что у `FB_VfdAdapter_Cond`: `xCommOk`, `xReady`,
   `xRunning`, `xFault`, `xWarning`, `xRemote`, `rSpeedAct_pct`, `wCtw`, `uiFref`; методы
   `Decode(wStw, uiFact, xSlaveOk)` и `Encode(xQReset, rSpeedRef_pct)`. Правила — [DESIGN.md](DESIGN.md),
   раздел 8.2: без связи слово состояния недостоверно (готов, в работе, авария — `FALSE`), скорость —
   последняя принятая; задание ограничено 0…100 %, NaN → 0. Если ПЧ пускается по сети, а не проводом,
   `Encode` берёт команду из `GVL_IO.xP10n_VfdQRun` — генератор её уже заполняет.
3. Заменить тип трёх экземпляров `fbVfdP101…fbVfdP103` в `PRG_FieldIn` (их `Encode` вызывает
   `PRG_FieldOut`).
4. Тесты адаптера — по образцу `tests/POUs/Field/FB_VfdAdapter_Cond_Test`: биты, масштаб, потеря связи,
   сброс, ограничение задания. Затем `python tools\codesys\cds.py check --tests` и `cds.py test`.
5. В самом ПЧ настроить сторожевой таймер связи: 5 с без запросов → предустановленные 50 Гц (04,
   раздел 12) — станция рассчитывает на это поведение при потере связи.

Модель ПЧ в имитации (`FB_VfdSim`) работает с той же условной картой; для имитации с новым адаптером её
регистры тоже нужно привести к карте своего ПЧ.

### 6.3 Уставки станции и регулятора

| Что | Где задаётся | Где меняется на работающем ПЛК |
|---|---|---|
| уставки устройств: шкалы, HH/H/L/LL, задержки, ожидание ОС, пусков в час, мин. частота | перечень сигналов (`sp_*`, `delay_*`, `params`) → `GVL_CfgProject` | `GVL_Persist.st<TAG>Cfg` |
| отметки уровней, выдержки, чередование, последовательный пуск, недогрузка | умолчания `ST_StationCfg` ([DESIGN.md](DESIGN.md), раздел 3.1), таблица [04_algorithms.md](04_algorithms.md), раздел 18.2 | `GVL_Persist.stStationCfg` |
| регулятор LIC101: Kp, Ti, пределы задания и выхода | `GVL_StationDefaults.stLIC101Cfg` и блок станции `GVL_Persist` | `GVL_Persist.stLIC101Cfg` |

Станция проверяет уставки каждый цикл: диапазон и порядок отметок уровня. Неверная запись не
применяется — станция работает по последней корректной копии, биты ошибок — в
`GVL_Station.stStationSts.wCfgErr`, принятое изменение — событие 101017 журнала; вернуть запись к
действующей копии — импульс `GVL_Station.stStationCmd.xRevertCfg`. Новые умолчания станции меняют вместе
в коде, в DESIGN и в 04: расхождение найдёт сверка документов. Значения, помеченные в 04 «сверить с
паспортом насоса» (пусков в час, мин. частота, порог недогрузки), на реальном объекте берут из паспорта
насоса и ПЧ.

### 6.4 Модель под свой объект

Параметры модели — `GVL_Sim.stSimCfg` (`ST_SimCfg`, [DESIGN.md](DESIGN.md), разделы 3.3 и 11.3): площадь
резервуара, отметка перелива, средний приток и суточный профиль, seed и параметры ливней, характеристика
насоса и сети (`stPump`: напор при нулевой подаче, крутизна, геометрический напор, сопротивление
трубопровода, КПД, номинальные мощность и ток), разгон ПЧ. Значения по умолчанию условные. Тесты ST модели
сравнивают результат с эталоном `tools_project/plant_reference.py`: при смене умолчаний меняют и эталон,
а `pytest` сверит числа документов с ним (`test_plant_reference.py`).

## 7. Частые проблемы

| Признак | Причина и что делать |
|---|---|
| клиент OPC UA получает `BadSecurityChecksFailed` | сертификат клиента не в доверенных рантайма: `python tools_project\codesys\sim.py pki` (перезапустит рантайм) |
| сервер предлагает только конечную точку `None`, вход отклонён | нет сертификата OPC UA-сервера: тот же `sim.py pki` |
| рантайм остановился во время серии | закончился двухчасовой демо-режим: `sim.py start --no-import --need-min <минут>` перед частью серии |
| `generate.py`: «iolistgen не найден» | установите пакет iolistgen или задайте `IOLISTGEN_REPO`; соседний каталог `../iolistgen` ищется сам |
| сборка: C0046 «GVL_Persist не задан» | импорт не создал объект Persistent Variables — запасной путь `tools_project\codesys\codesys_pvl.py` ([MANUAL_STEPS.md, раздел 9.3](MANUAL_STEPS.md#93-persistent-variables)) |
| сценарий: шаг `reset` — «не проверялось» | нет `CODESYS_EXE` или `PMI_RESET=none`: сброс приложения OPC UA не умеет, его делает `sim.py reset` |
| `ScenarioTimeout … не выполнено за N с контура` | реакция не наступила за таймаут; в тексте — условие и последнее значение; проверьте И0 и инъекции, оставшиеся от прошлых действий (`SimCmd.xClearFaults`) |
