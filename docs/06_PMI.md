## 1. Объект испытаний

ПО ПЛК КНС-1 в сборке имитации: логика станции (`PRG_Station`), слой устройств (iolistgen по
[03_io_list.csv](03_io_list.csv)), полевой слой, журнал событий, модель объекта и инъекция отказов,
экраны WebVisu. Оборудование объекта (ПЛК210, ПЧ, датчики, шкаф) в испытаниях не участвует: его
заменяет модель, которая пишет те же переменные `GVL_IO`, что и драйверы (решение D-01 архитектуры).

## 2. Цель испытаний

Подтвердить на модели объекта, без оборудования, что ПО выполняет функции Ф1–Ф12, Ф14, Ф15 ТЗ:
нормальная работа в двух способах регулирования, чередование, АВР, отказ уровнемера, сухой ход,
аварийный уровень, потеря связи с ПЧ, смена режимов, пропадание и восстановление питания, тревоги
ISA-18.2, журнал и суточный режим работы. Функция Ф13 (обмен с верхним уровнем) проверяется в
проекте plc-iiot-stack.

## 3. Общие положения

- Испытания проводит инженер АСУ ТП по этому документу; результаты — в протоколе
  [07_test_protocol.md](07_test_protocol.md).
- Идентификатор проверки `PMI-NN` — ключ для автоматизированного сценария
  (`scenarios/pmi/PMI-NN.toml`, [DESIGN.md](DESIGN.md), раздел 14.3), для колонки `pmi` перечня
  тревог и для протокола. Номера не переиспользуются: исключённая проверка остаётся в таблице с
  пометкой «исключена».
- Ожидаемые результаты написаны в именах ПО (пути переменных, коды и номера тревог), чтобы сценарий
  проверял их без толкования. Если реализация переименует переменную, документ правится вместе с ней:
  `test_scenario_files.py` сверяет пути сценариев с символами проекта.
- Сборка имитации не загружается в ПЛК объекта: в сборке ПЛК210 имитация запрещена (решение D-02).

### 5.2 Исходное состояние И0

Перед каждой проверкой, если в ней не сказано иное:

1. Сборка имитации загружена и запущена, `GVL_Sim.xSimulation = TRUE` (тревога `KNS1.SIM` — норма
   стенда).
2. Модель: `SimCmd.xResetPlant` (уровень `SimCfg.rLevelInit_m` = 1,20 м, время перелива
   `SimSts.udiOverflow_s` = 0, ливни сняты, ПЧ готовы), `SimCmd.xClearFaults` (все инъекции сняты).
3. Приток постоянный: `SimCmd.xInflowOverride = TRUE`, `SimCmd.rInflowOverride_m3h = 100`.
4. Ускорение `SimCfg.rTimeScale` — по проверке (колонка «k» приложения А), по умолчанию 20.
5. Отказы сброшены, тревоги квитированы: `Cmd.xResetAll`, затем `Cmd.xAckAll`.
6. Уставки устройств, станции и LIC101 — по умолчанию ([04_algorithms.md](04_algorithms.md), раздел
   18): `GVL_Hmi.xApplyProjectCfg`.
7. Станция в «Автомате» (`Cmd.xSetAuto`), способ — по проверке; насосы Н1–Н3, регулятор LIC101 и вентилятор В1
   в `Auto` (`Hmi.stP10nCmd.stCommon.xSetAuto`, `GVL_Station.stLIC101Cmd.stCommon.xSetAuto`,
   `Hmi.stV1Cmd.stCommon.xSetAuto`: режимы энергонезависимы, после первой загрузки — `Manual`; без этого ПИД не
   готов, 04 §7.4, и В1 не пускается автоматикой, 04 §17), переключатели «Дистанционное»
   (`Inj.axLocal[1..3] = FALSE`).
8. Наработка (наладочная запись `GVL_Persist.stP10nRetain.udiOpTime_s`, пока насосы стоят): Н1 —
   360 000 с (100 ч), Н2 — 720 000 с (200 ч), Н3 — 1 080 000 с (300 ч); ведущим выбирается Н1. Если
   проверке нужен другой ведущий, это сказано в ней.
9. Пуски насосов в окне часа (`fbP10n.stSts.uiStartsLastHour`) — не ближе трёх к пределу
   `uiMaxStartsPerHour`: иначе выдержка с остановленными насосами и притоком 0 (при k = 50), пока старые пуски
   не выйдут из окна. В серии на имитаторе пуски набираются быстрее, чем на объекте: короткие проверки идут
   подряд при k = 20, и ведущий упирался в предел (прогон 19.10.2026).

### 5.3 Время и ускорение

Ускоряется весь замкнутый контур: модель, таймеры устройств и станции, ПИД, тревоги, журнал — общими
часами `FB_ScaledClock` с коэффициентом `SimCfg.rTimeScale` (решение D-07, [ARCHITECTURE.md](ARCHITECTURE.md),
раздел 11). Поэтому:

- все времена в таблицах — **время контура**: выдержка 30 с при k = 20 проходит за 1,5 с реального
  времени. Сценарий задаёт таймауты во времени контура, исполнитель делит их на k;
- k ≤ 50 (k · 20 мс ≤ 1 с: шаг ПИД меньше `tDtMax`, задержки DI в 1 с различимы). Проверки качества
  регулирования (PMI-04, PMI-05, PMI-07, PMI-11) — при k ≤ 20, чтобы шаг времени за цикл (≤ 0,4 с)
  был меньше периода расчёта ПИД `tSample` = 0,5 с;
- допуск по времени — ±1 цикл `MainTask` во времени контура (k · 20 мс) плюс период опроса
  исполнителя, умноженный на k. Между записями журнала устройства и станции — до +3 циклов: станция
  видит выход устройства циклом позже, выдержка срабатывает в первом цикле после неё, а начало цикла
  пользовательского рантайма Control Win (Windows, не реального времени) смещается ещё до цикла
  (прогон ПМИ 19.10.2026);
- наработка насосов в имитации растёт в k раз быстрее реального времени: это данные стенда, не
  объекта (их меняет только наладочная запись И0).

### 5.4 Средства имитации

Инъекции отказов и команды модели — переменные `GVL_Sim`, они же — кнопки экрана «Имитация»
([08_hmi_spec.md](08_hmi_spec.md), раздел 10). Имена — по [DESIGN.md](DESIGN.md), раздел 3.3.
Инъекции действуют только при `GVL_Sim.xSimulation = TRUE`.

Команды модели `SimCmd` = `GVL_Sim.stSimCmd`, параметры `SimCfg` = `GVL_Sim.stSimCfg`:

| Поле | Тип | Что делает |
|---|---|---|
| `SimCfg.rTimeScale` | `REAL` | ускорение контура, 1…50 (раздел 5.3) |
| `SimCmd.xResetPlant` | `BOOL`, импульс | уровень := `SimCfg.rLevelInit_m`, время перелива `udiOverflow_s` := 0, ливни сняты, ПЧ готовы |
| `SimCmd.xClearFaults` | `BOOL`, импульс | снять все инъекции `Inj` |
| `SimCmd.xSetLevel`, `rSetLevel_m` | `BOOL` импульс, `REAL` | установить уровень в модели (подготовка проверки) |
| `SimCmd.xInflowOverride`, `rInflowOverride_m3h` | `BOOL`, `REAL` | постоянный приток вместо суточного профиля и ливней |
| `SimCmd.xStormNow`, `rStormPeak_m3h`, `tStormDuration` | `BOOL` импульс, `REAL`, `TIME` | ливень сейчас: трапеция с пиком `rStormPeak_m3h` (при `xInflowOverride = FALSE`) |
| `SimCmd.xSetTimeOfDay`, `rTimeOfDay_h` | `BOOL` импульс, `REAL` | время суток модели (суточный профиль 27…112 м³/ч, среднее 70 м³/ч) |
| `SimCmd.xPressReset`, `xPressSilence` | `BOOL`, импульс | нажатие кнопок `HS501` «Сброс аварий» и `HS502` «Отключить звук» |
| `SimCmd.xDoorOpen` | `BOOL` | дверь павильона открыта (`ZS404`) |
| `SimCfg.rAirTemp_C` | `REAL` | температура воздуха в павильоне (`TT403` по RS485-2) |
| `SimSts` = `GVL_Sim.stSimSts` | только чтение | истинный уровень, приток, подача насосов, частоты, токи, время суток, перелив `udiOverflow_s` |

| Поле | Тип | Что видит ПЛК |
|---|---|---|
| `axVfdFault[i]` | `BOOL` | авария ПЧ: реле «Авария» `P10n_FLT = TRUE`, бит 2 слова состояния, код аварии `P10n_FCODE` = 11 (`SIM_VFD_FCODE_EXT`, условный); ПЧ выбегом останавливает насос; авария снимается сбросом ПЧ после снятия инъекции |

| `axFeedbackStuck[i]` | `BOOL` | реле «ПЧ в работе» залипло: `P10n_RFB = TRUE` |
| `axAirLock[i]` | `BOOL` | сухой ход насоса: подача 0, ток на 100 % частоты ≈ 11 А (меньше порога 12 А) |
| `axClog[i]` | `BOOL` | засор рабочего колеса: подача −60 %, ток ≈ 1,3 × тока до засора (на 100 % — выше 34 А; требование к модели для PMI-15) |
| `axOverheat[i]` | `BOOL` | перегрев обмотки: `TS1n2` сработал, цепь аварии ПЧ разомкнута (авария ПЧ) |
| `axLeak[i]` | `BOOL` | протечка в камеру статора: `MS1n3` сработал |
| `axVfdCommLoss[i]` | `BOOL` | ПЧ не отвечает: `GVL_IO.xMbOk_RS485_1_Sn = FALSE`, регистры замирают; через 5 с без запросов ПЧ переходит на 50 Гц (сторожевой таймер ПЧ, [04_algorithms.md](04_algorithms.md), раздел 12; модель ПЧ — так же). Все три — потеря линии RS485-1 |
| `axLocal[i]`, `axLocalRun[i]` | `BOOL` | переключатель `HS1n4` в «Местное»; пуск с местного поста (ПЧ — на частоте местного поста 50 Гц, `SIM_VFD_LOCAL_FREQ_HZ`) |
| `aeAiFault[k]`, `arAiForced_mA[k]` | `E_SimAiFault`, `REAL` | сигнал 4–20 мА датчика, индекс `SIM_AI_*`: 1 LT101, 2 PT201, 3 FT202, 4 AT401, 5 AT402. Значения: `WireBreak` 0 мА, `FailLow` 3,0 мА, `FailHigh` 22 мА, `UnderRange` 3,7 мА, `OverRange` 20,8 мА, `Freeze` — последнее значение, `Forced` — ток `arAiForced_mA[k]` |
| `eLs102Stuck`, `eLs103Stuck` | `E_SimFloatStuck` | поплавок: `None`, `StuckNormal` (не срабатывает), `StuckTripped` (сработал и не возвращается; то же — обрыв цепи НЗ-контакта) |
| `xPowerLoss` | `BOOL` | нет напряжения на вводе: `ES301 = FALSE`, ПЧ обесточены, ИБП на батареях (`YS302`) |
| `xUpsFault` | `BOOL` | неисправность ИБП (`YS303`) |
| `xTempCommLoss` | `BOOL` | датчик `TT403` (RS485-2) не отвечает |
| `xFanFault` | `BOOL` | авария вентилятора В1 (`V1_FLT`) |
| `xFanNoFeedback` | `BOOL` | блок-контакт пускателя В1 (`V1_RFB`) не замыкается при поданной команде: `V1.FTS` при пуске, `V1.FBL` в работе |
| `xValveChamberFlood`, `xFire` | `BOOL` | затопление камеры задвижек (`LS203`), пожар (`YS405`) |
| `rH2S_mgm3`, `rCh4_pctLel` | `REAL` | концентрации газов вместо фоновых; < 0 — фон модели |

### 5.5 Порядок проведения и оценка

- Каждая проверка начинается из И0 (раздел 5.2), если не указано иное. Действия выполняются с HMI
  (кнопки экранов) или записью переменных онлайн; сценарий выполняет те же записи (приложение А).
- Итог: «соответствует» / «не соответствует» (с номером замечания) / «не проверялось» (с причиной).
- Сокращения: `Sts` — `GVL_Station.stStationSts`, `Cmd` — `GVL_Station.stStationCmd`, `Cfg` —
  `GVL_Persist.stStationCfg`, `fbP101` — `GVL_Devices.fbP101` (и остальные устройства),
  `Hmi.stP101Cmd` — `GVL_Hmi.stP101Cmd`, `Inj`, `SimCmd`, `SimCfg`, `SimSts` — раздел 5.4.
- Тревога в ожидаемом результате — код (номер) и состояние ISA-18.2: `ActiveUnack`, `ActiveAck`,
  `RtnUnack`, `Normal`, `Shelved`, `SuppressedByDesign`, `OutOfService`. Тревоги устройств видны в
  `stSts.stCommon.wAlmActive` (бит = слот), станции — в `Sts.wAlmActive` (бит = slot − 1), все
  тревоги не в состоянии `Normal` (в том числе отложенные и подавленные) — в `GVL_Log.stAlarmView` и на
экране «Тревоги»; события — в журнале.
- «Не позже» и «через» — время контура (раздел 5.3) с допуском раздела 5.3.

## 7. Метрологическое обеспечение

Средства измерений в испытаниях на имитаторе не применяются: измеряемые величины задаёт модель, а
