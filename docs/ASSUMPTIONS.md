## Исходники и сборка

| № | Допущение | Статус | Обоснование / где проверить |
|---|---|---|---|
| B1 | Источник истины — тексты ST в `src/`, `.project` в git не хранится | принято | `.project` бинарный: его нельзя ревьюить и сливать. Готовые `.project` и `.library` прикладываются к релизам GitHub |
| B2 | Свойства в `build/assembled/` записываются в синтаксисе RuSTy: `PROPERTY_GET <Имя> : <тип> ... END_PROPERTY`, `PROPERTY_SET ...` | принято | В МЭК 61131-3 ред. 3 свойств нет; RuSTy понимает такой синтаксис. Собранный текст нужен только анализаторам и в CODESYS не импортируется |
| B3 | Вариант сборки `iec-checker` понижает конструкции, которые не разбирает iec_checker (методы внутри ФБ, `EXTENDS`, прагмы) | принято | Только для статанализа; семантика собранного текста может отличаться от исходной |
| B3a | Понижение может менять смысл ради разбора: `TIME()`/`LTIME()` → вызов заглушки `CDS__TIME()`, `a[i].x` → `a.x[i]`, вызов `afb[i](...)` → `afb(..., i)`, пустая ветвь → `CDS__NOP();`, невычисленная граница массива → `0..32767`, имена — ключевые слова iec_checker → суффикс `_` | принято | Иначе iec_checker 0.4 не разбирает весь файл (ParserError), и его находки теряются целиком. Проверено прогоном на копиях plc-process-lib (91 объект `src/` и `tests/`) и s7-to-codesys (54 объекта): ошибок разбора 0; у plc-process-lib, где таких конструкций в коде нет, набор находок тот же (1427 обоснованных, 176 артефактов), в копии с возвращёнными исходными формами (`Priority`, `LTIME()`, `afbAlarm[i](...)`, `a[i].x`, `WORD#1`, константы в границах) — тоже 0 ошибок разбора (до понижения — 6), а находки отличаются только на изменённых строках. Цена: часть находок не выдаётся (PLCOPEN-N3 у переименованных имён, OutOfBounds у невычисленных границ и массивов в `STRUCT`, PLCOPEN-CP13 у рекурсии методов) или выдаётся ложно (UnusedVariable у массива, к которому обращаются только как `a[i].x`). Список замен и их влияние — `tools/README.md`, «Понижение для iec_checker» и «Что понижение скрывает и добавляет» |
| B3b | Вариант сборки `rusty` понижает `VAR_IN_OUT CONSTANT` до `VAR_IN_OUT`; преобразования TIME ↔ целые объявлены в прокладке | принято | RuSTy 1.0.6 не знает модификатора (E034, E036 в вызовах) и этих преобразований (E048). Запрет записи в параметр и точность преобразований (в RuSTy `TIME` — 64 бит, нс; в CODESYS — 32 бит, мс) RuSTy не проверяет — их проверяет компилятор CODESYS (`cds.py build`, `check`) |
| B4 | GVL объявляются с `{attribute 'qualified_only'}`, обращение — `GVL_Const.ИМЯ` | принято | Рекомендуемая практика CODESYS: нет конфликтов имён. RuSTy не знает имён GVL — вариант сборки `rusty` убирает префикс `GVL_Const.` (проверено: `plc --check` по `build/assembled/rusty/` проходит) |
| B5 | Режимы в `FB_Example` разбираются `CASE` по перечислению `E_DeviceMode` | принято | iec_checker 0.4 не разбирает метки `CASE` вида `E_DeviceMode.Auto` и неконстантные начальные значения (`:= E_DeviceMode.OutOfService`, `:= GVL_Const.ИМЯ`). Код пишется для CODESYS, а понижение — забота варианта сборки `iec-checker`: метки заменяются целыми значениями, неконстантные начальные значения убираются |
| B6 | Строковые литералы `STRING` (имена тестов, сообщения CfUnit) — только ASCII | принято | Кириллица в `STRING` зависит от кодовой страницы среды и рантайма. Комментарии остаются русскими |
| B7 | Обязательный статанализ в CI — iec_checker v0.4 (тот же, что локально); образ `nightly` — необязательное задание | принято | Обоснования в `iec_checker_allow.toml` подобраны под находки v0.4: с другой версией разборщика обязательная проверка зависела бы от его изменений. Бинарник v0.4 закреплён по размеру и SHA-256 (у релиза нет опубликованной суммы — она вычислена по файлу), образ `nightly` — по дайджесту |

## Семантика F_Clamp

`F_Clamp(rValue, rLow, rHigh)` возвращает `rValue`, ограниченное отрезком между границами.

- Границы включаются: `F_Clamp(rLow, rLow, rHigh) = rLow`, `F_Clamp(rHigh, rLow, rHigh) = rHigh`.
- **Если `rLow > rHigh`, границы меняются местами.** Результат всегда лежит между двумя заданными
  числами и не зависит от порядка аргументов. Альтернативы были такие: вернуть `rLow` или повторить
  поведение `LIMIT` (`MIN(MAX(IN, MN), MX)` при `MN > MX` всегда даёт `MX`). Обе дают результат на
  одной из границ при любом входе, и ошибку конфигурации легко не заметить. Функция с результатом
  `REAL` не может сообщить об ошибке, поэтому выбрано поведение без скачков.
- Вырожденный отрезок `rLow = rHigh` — результат всегда равен границе.
- NaN не обрабатывается: при `rValue = NaN` результат — NaN. Достоверность измерения проверяется
  до вызова (NAMUR NE 43 — в ФБ аналогового входа).
